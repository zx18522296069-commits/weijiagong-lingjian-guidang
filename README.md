# 未加工零件自动归档系统

本项目在 GitHub Actions 云端执行，Mac 关机不影响运行。

## 当前正式业务口径

系统固定按下面顺序理解数据：

1. **“正在加工”订单目录**：当前订单范围。
2. **每个订单目录中的正式汇总表**：当前订单事实源；无法唯一确定时禁止猜测。
3. **《累计加工台账.xlsx》**：永久累计事实，保存累计状态、加工流水、板材入账记录、异常记录和已退出历史。
4. **《当前待加工零件.xlsx》**：动态视图，由当前订单事实 + 永久累计事实完整重建。
5. **“拆图结果”根目录完成文件**：本轮待处理板材；不扫描“已录入数量”子目录。

订单目录数量、可用订单汇总表数量、本次扫描板材数量是三个不同概念，日志和控制台不得互相混用。

## 正式运行流程

系统采用：

**增量读取，完整核验，批量入账，全量重建视图，幂等归档。**

执行顺序：

**增量扫描 → 只下载变化文件 → 整板校验 → 批量累计 → 完整重建结果视图 → 本地校验 → 上传 metadata/hash 验证 → 成功后归档。**

同一轮多个合格板材只批量提交一次，两份正式 Excel 各最多上传一次。Google Drive 两个文件采用可恢复顺序事务：

1. 本地生成两份正式 Excel；
2. 本地 openpyxl 校验；
3. 上传《累计加工台账》并核对 Drive md5Checksum 与 size；
4. 上传《当前待加工零件》并做相同核对；
5. 使用已确认的本地文件做语义验证；
6. 两份都成功后，才统一归档新入账和补归档板材；
7. 最后提交 runtime state。

**上传后禁止为了验证而重新下载整个 Excel。** 如果累计台账上传成功、当前待加工上传失败，本轮不归档、不提交新 runtime state；下一轮发现累计台账 MD5 改变后重新读取正式累计事实，并利用完整板材号 + 内容指纹避免重复扣减。

## 持久化 runtime state

正式生产使用：

`runtime_state/state.json`

GitHub Actions cache 在不同 runner 之间恢复这个目录和正文缓存。生产 cache 使用统一前缀 `weijiagong-runtime-production-`，每次成功 production 使用本次 run id 保存新的唯一 key。

state 至少保存：

- `state_schema_version`；
- 每个订单源的 file id、modifiedTime、md5Checksum、父目录、订单目录名和标准化 source records；
- 正式累计文件 ID、modifiedTime、md5Checksum、size；
- 已解析 existing state、historical rows、flows、board records、anomalies、posted board keys 等累计索引。

runtime state **只是性能缓存，不是业务事实源**。缓存不存在、损坏、schema 不兼容或正式累计 MD5 改变时，自动回退真实 Google Drive 初始化；初始化成功后重新生成缓存。

只有 **production 且整次任务成功** 后才保存新的生产 cache。dry-run 可以读取生产 cache 加速，但不得覆盖它。

## 订单源增量扫描

订单源签名至少使用：

`file_id + modifiedTime + md5Checksum + parent_folder_id + order_container_name`

每轮区分 `unchanged / added / modified / removed`：

- unchanged：复用标准化记录，不下载 Excel；
- added：只下载新增文件；
- modified：只下载修改文件，按 file id 替换旧缓存，禁止 append；
- removed：从活动 source cache 移除。历史剩余为 0 的永久保留为退出完成历史；历史剩余非 0 的冻结上一次有效状态并提示异常。

订单业务键：`订单号 + 图号 + 厚度 + 坡口`。业务键没变时允许采用新的订单事实重新计算，但历史累计加工量必须保留；如果新订单数量小于累计加工数量，允许负数。业务键变化导致历史流水无法唯一对应时必须冻结，禁止猜测迁移。

## 累计台账增量读取

启动时先比较正式累计台账 metadata。若 Drive 的文件 ID、modifiedTime、MD5、size 与 runtime state 一致，直接使用 parsed ledger，**累计 Excel 正文下载为 0**。

只有 cache 缺失/损坏/schema 变化、正式累计 MD5 变化或明确初始化时才重新下载累计 Excel。

真正无变化且拆图结果根目录为空时，在 metadata 扫描后快速退出：订单 Excel 下载 0、累计 Excel 下载 0、完成文件下载 0、正式 Excel 上传 0。

## 板材处理规则

每次运行只扫描“拆图结果”根目录直接存在的完成 Excel。每张板独立整板预校验：任意阻断行失败，则整张板不入账、不移动，文件继续留在根目录。

阻断包括：订单找不到、图号无法唯一匹配、厚度/坡口无法唯一确认、基础数量或基础总重量不一致、文件损坏、同板材号内容冲突等。

完整板材号规则：

- `#2323`、`#2323-1`、`#2323-2` 是独立板材；
- 同完整板材号 + 同内容指纹：不重复累计，只作为补归档候选；
- 同完整板材号 + 不同内容指纹：阻断为 `同板材号内容冲突`；
- 早期无内容指纹历史必须重新核对当前文件、永久流水和板材入账记录，能唯一证明一致才补归档，否则阻断。

## 超加工

基础身份和业务资料正确，只是本次加入累计后 `当前剩余 < 0`，不作为阻断：

- 累计数量照实正式入账；
- 当前剩余保留负数，禁止自动改成 0；
- 状态为 `超加工/待核查`；
- 整行红色；
- 《异常记录》永久增加 `超加工/待核查` 记录。

## 状态与当前视图

两份正式 Excel 的零件明细统一使用同一套颜色规则：

- `未加工`：**无底色**
- `部分完成`：**黄色**
- `已完成`：**绿色**
- `超加工/待核查`：**红色**

该规则同时适用于《累计加工台账.xlsx》和《当前待加工零件.xlsx》。不再使用“未开始”。

订单没有整体完成时，该订单必须完整显示，已经完成的零件也保留绿色；尚未开始加工的零件保持无底色。只有该订单全部零件 `当前剩余 == 0` 且没有阻止订单完成的异常，整个订单才从《当前待加工零件》退出；《累计加工台账》永久保留。

## 控制台结果口径

“未加工更新运行结果”只围绕**本次扫描板材**显示：

- 本次扫描 X 张
- 成功录入 Y 张
- 重复已处理 Z 张
- 未成功 N 张

必须满足：`Y + Z + N = X`。

订单目录数和订单源数不能当成板材数。每张未成功板材必须显示板材号、状态、具体原因和下一步。订单源缺失或内容错误单独显示为“订单源 / 资料异常”，不混入板材数量。

## 日志与性能统计

每轮日志明确打印：

- 当前订单源数量与 unchanged / added / modified / removed；
- 累计 cache 命中状态和是否需要下载正式累计 Excel；
- 根目录待处理板材数，以及新入账、补归档、阻断结果；
- 本轮 Drive 正文下载总数及订单源 / 累计台账 / 拆图结果分类；
- 正式 Excel 实际上传次数；
- cache、metadata 扫描、Drive 正文读取、Excel 解析、拆图核验、状态重建、Excel 生成、本地验证、上传、metadata/hash 验证和总耗时。

## dry-run / 只读测试

`TEST_MODE=true` 是正式数据的只读演练：可以读取生产 cache，但不写正式 Drive、不移动拆图结果、不覆盖生产 runtime cache。未来如果建立独立测试目录，再单独称 `test-folder`。

## 正式台账自愈

每次运行都在“正在加工”根目录按正式文件名重新发现《累计加工台账.xlsx》和《当前待加工零件.xlsx》，不依赖历史固定 file ID。

文件夹、快捷方式、近似名称不能冒充正式表，同名正式文件多于一个时阻断。仅《当前待加工零件》缺失时，必须使用当前订单事实 + 现有累计历史重建，不能把历史累计清零。累计台账缺失时才允许按当前完整订单建立新的零累计基线；订单源不完整时禁止重建。

## 定时与触发

本仓库自身**不维护第二套固定业务 cron**。当前最终架构：

- 前端立即执行：生产控制台通过 `workflow_dispatch` 触发 production；
- 前端定时执行：生产控制台保存北京时间计划，由控制台后台调度器到点触发 `workflow_dispatch`；
- GitHub 页面人工执行默认 `test`；正式补跑需显式选择 `production`；
- 自动时间只在生产控制台维护。
